# Política de integración de programas

## Responsabilidad del maestro

El maestro organiza relaciones entre objetivos, competencias, mallas y recursos. Cada programa especializado conserva la responsabilidad de sus clases, índices, prácticas, fuentes y versiones.

Se usa una arquitectura federada: un registro común describe cómo consultar unidades con estructuras distintas. El contrato compartido no obliga a renombrar las carpetas de los programas.

## Revisión antes de proponer cambios

1. Confirmar el repositorio exacto y su acceso.
2. Leer instrucciones de agentes y documentación vigente.
3. Identificar estructura de clases, módulos, talleres y laboratorios.
4. Leer los estándares pedagógicos y sus mecanismos de validación.
5. Revisar el contenido específico que se pretende conectar.
6. Clasificar su contribución al objetivo.
7. Documentar cambios mínimos y cómo se verificarían.

El README permite identificar alcance y puntos de entrada. Una equivalencia entre competencias necesita evidencia más específica.

## Ficha de correspondencia

Cada correspondencia futura debe registrar:

| Campo | Uso |
| --- | --- |
| Programa e ID | Identidad estable del origen |
| Unidad y ruta | Ubicación exacta del contenido |
| Referencia de versión | Commit o versión cuando se haya obtenido; SHA de archivo diferenciado |
| Fecha de lectura | Momento de revisión |
| Competencia y objetivo | Qué relación educativa se propone |
| Alcance | Introduce, practica, profundiza o evalúa |
| Evidencia observada | Sección o actividad que respalda la relación |
| Requisitos | Conocimientos y condiciones necesarios |
| Estado | Candidata, revisada por unidad, aplicada y revisada |
| Brechas | Qué parte del objetivo permanece descubierta |

La etiqueta aplicada y revisada requiere un registro de uso; no se deduce del contenido escrito.

## Solapamiento y complementariedad

Si dos programas tratan un mismo concepto, el maestro revisa nivel, propósito y aplicación. Puede ser razonable mantener ambos cuando desarrollan perspectivas diferentes.

El registro explica qué recurso conviene para la malla y qué aporta el otro. Una equivalencia candidata no elimina la necesidad de practicar en el nuevo contexto.

## Actividades puente

Una actividad puente resuelve una transición: vocabulario diferente, requisito faltante, cambio de contexto o conexión entre dos dominios.

Debe incluir una tarea breve y concreta, datos o materiales, evidencia esperada, revisión y conexión de salida. Las cinco mallas de esta entrega incorporan actividades originales de este tipo.

## Estados separados

- **Disponibilidad:** el recurso puede consultarse o todavía debe desarrollarse.
- **Revisión:** qué documento o unidad se leyó y con qué criterio.
- **Alineación:** hasta dónde se comprobó la correspondencia con un objetivo.
- **Aprendizaje:** qué demuestra la evidencia de una persona.

No se infiere el cuarto estado a partir de los tres primeros.

## Cambios de nombre y enlaces

Conserva el ID interno del programa cuando cambie su nombre. Verifica redirección o nueva URL y actualiza las referencias con fecha. Si un programa se retira, conserva su historial y marca las mallas afectadas.

No se debe cambiar una fuente para hacer desaparecer un error del validador. Primero se entiende la causa; después se corrige o se registra la brecha.

## Licencias

La consulta y el enlace no modifican licencias. Si se necesita incorporar contenido externo, se revisan términos, atribución y compatibilidad antes de copiarlo. Los contenidos propios del maestro se identifican como tales.
